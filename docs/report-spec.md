# 六项战报口径

战报的唯一作用是让明天比今天更准。所以每一项都必须可核对、可归因，不能有"感觉投了不少"这种描述。

---

## 固定六项

### 1. 投递数：目标 vs 实际

```
投递数 = 当日 status='success' 的记录数
目标   = 配置中的 daily_cap（不是拍脑袋的愿望）
偏差   = 目标 - 实际
```

偏差必须写原因，四选一（可多选）：

| 原因 | 判定依据 |
|---|---|
| 候选池不足 | 搜索返回量 < 剩余额度 |
| 熔断停机 | 当日有 needs_human / fail_streak 触发记录 |
| 人工接管耗时 | 接管时长超过 15 分钟 |
| 时间不够 | 达到 session_max_minutes |

"没有原因"等于没做归因，这条战报不合格。

### 2. 重复拦截

按来源拆开计数：历史台账 / 跨平台近似 / 批内重复。

这个数字不是越低越好。拦截率高说明候选池在收窄，通常意味着该换关键词或换城市；拦截率为 0 则要怀疑去重是否生效了。

### 3. 站内消息

四分类：需回复 / 已回复 / 仅知晓 / 系统通知。

按渠道标注来源（猎聘 IM / BOSS / 智联 / 邮箱 / 其他）。不同渠道的消息由不同流程处理，混在一起统计会漏。

### 4. 邮件收发

- 发送成功封数（以 SMTP 返回成功计，不以"已提交队列"计）
- 退信数
- 需回复未回数

目标 20 封/日，去重与黑名单剔除后不足不硬凑。

### 5. 黑名单生效确认

抽 3 条当日被拦下的记录，人工看是否误杀。抽样而不是全查——目的是确认闸门在工作，不是逐条审计。

发现误杀要立刻移出黑名单，并把规则收紧到更精确的匹配方式。

### 6. 次日计划

- 时段安排（哪个时间段跑哪个平台）
- 候选池余量（符合条件且未投的岗位还剩多少）
- 待修项（页面改版、职级写错、缺失字段）

---

## 输出格式

存两份，一份 Markdown 给人看，一份 JSON 给程序读：

```
reports/2026-11-19.md
reports/2026-11-19.json
```

Markdown 结构固定六节，标题不要改，便于逐日对比。JSON 用扁平 key，便于画趋势。

## 三条铁律

1. **以本地台账为准，不以平台页面数字为准。** 平台统计有延迟，也会把"查看"算成"沟通"。
2. **以成功态为准，不以点击次数为准。** 点了不等于投了。
3. **以当日切分，跨日不合并。** 23:50 和次日 00:10 是两天，不要为了凑数合并。
