# 去重规则与台账字段规范

这套东西真正的价值在这个文件，不在点击脚本。点击脚本谁都能写，但「投了 1800 次不重复、不丢账、能复盘」需要规则。

---

## 1. 三源去重

投递前必须依次过三道闸，任一命中即跳过，且**记录跳过原因**（不是为了投，是为了事后能解释"为什么这个岗位没投"）。

```
候选岗位
  ├─ 闸1 黑名单      → 命中：BLOCKED，不写投递记录，只写跳过记录
  ├─ 闸2 历史台账    → 命中：DUPLICATE，不调 apply，只更新 last_seen
  └─ 闸3 当日批内    → 命中：DUPLICATE（批内去重），不调 apply
        ↓
     调用 adapter.apply()
```

**顺序不可调换。** 黑名单必须前置：如果先投后拦，等于污染了台账，还会让平台真的收到一次投递。历史台账其次：能在本地判断的，不要浪费一次页面请求。

### 闸1：黑名单

三类，配置里分开维护：

| 类型 | 示例 | 匹配方式 |
|---|---|---|
| 公司黑名单 | 已面过且拒、已拉黑、竞业限制 | 公司名归一化后精确或前缀匹配 |
| 行业黑名单 | 制药、CRO/CDMO、医药器械 | 平台行业标签包含即命中 |
| 岗位关键词黑名单 | 销售、保险代理人、品检员 | 标题分词后包含即命中 |

公司黑名单支持域名/集团级：同一集团多地址、多主体，按一条线索算，避免"换个马甲又投一遍"。

### 闸2：历史台账

以 `platform + job_id` 为主键查。另加一层**跨平台近似判断**：

```
company_norm 相同 且 title_norm 相同 且 city 相同
```

三条全中即视为疑似重复，默认跳过并记 `cross_platform_dup`。同名岗位在同一城市挂两个平台，大概率是同一家公司的同一个坑。

例外：如果 `jd_hash` 不同且 `posted_at` 相差超过 30 天，视为重新开放，允许投。

### 闸3：当日批内

同一批次内，`job_id` 或跨平台近似任一命中即跳过。搜索接口翻页有重叠是很常见的，不做批内去重会重复投。

## 2. 归一化规则

去重的准确率全在这一节。规则要固定、可测试、不要"看起来差不多"。

### company_norm

按顺序执行：

1. 全角转半角，中文括号 `（）` 转 `()`，去掉所有空白字符
2. 去掉括号及其内容：`迈得医疗工业设备股份有限公司(Maider Medical,688310.SH)` → `迈得医疗工业设备股份有限公司`
3. 若以「分公司」结尾，先剥离暂存；主体后缀按**任意位置**删除（长的先删，否则 `股份有限公司` 会残留 `股份`）：`股份有限公司` `有限责任公司` `集团有限公司` `有限公司` `集团` `公司`；最后把「分公司」拼回
4. 去掉 `·` `-` `_`，英文转小写

**不删地域前缀**。看似能合并「台州XX」与「XX」，实际会误伤品牌名（`北京汽车` → `汽车`、`上海电气` → `电气`），误合并比漏合并更难排查。地域差异交给 `city_norm` 处理。

结果示例：

| 原始 | 归一化 |
|---|---|
| 迈得医疗工业设备股份有限公司（Maider Medical，688310.SH） | 迈得医疗工业设备 |
| 沃尔沃汽车台州工厂 | 沃尔沃汽车台州工厂 |
| 北京汽车股份有限公司株洲分公司 | 北京汽车株洲分公司 |
| 某某制药有限公司 | 某某制药 |

注意 `分公司` 保留，因为「北汽株洲分公司」和「北汽股份」是两个用工主体，合并会误判。

### title_norm

1. 全角转半角、去空白
2. 去掉括号内容：`质量管理/测试工程师(台州)` → `质量管理/测试工程师`
3. 去掉职级前缀：`高级` `资深` `Sr.` `Senior` `Junior` `初级`
4. 去掉薪资与地点尾巴
5. `/` 统一为 `·`，便于比较

`质量管理/测试工程师` 和 `质量经理` 归一化后**不同**，这是对的——职级不同就是不同岗位，不该被判重复。

### city_norm

只到市级。`台州` `台州市` → `台州`；`温岭市` 归属 `台州`（区县不单独成键，否则同一岗位在不同区县发布会被判成两个）。

## 3. 台账字段

存储用 SQLite，一行一次投递尝试。不用 CSV：并发写会坏，且无法做唯一约束。

```sql
CREATE TABLE applications (
    id              INTEGER PRIMARY KEY,
    platform        TEXT NOT NULL,
    job_id          TEXT NOT NULL,
    company         TEXT NOT NULL,
    company_norm    TEXT NOT NULL,
    title           TEXT NOT NULL,
    title_norm      TEXT NOT NULL,
    city            TEXT NOT NULL,
    city_norm       TEXT NOT NULL,
    salary_raw      TEXT,
    url             TEXT,
    jd_hash         TEXT,
    status          TEXT NOT NULL,      -- pending/success/duplicate/blocked/failed/skipped/needs_human
    reason          TEXT,
    evidence        TEXT,               -- 证据文件相对路径
    resume_version  TEXT,               -- 简历文件大小+上传时间，如 "568994B@2026-11-19"
    account         TEXT,               -- 账号指纹（脱敏后），多账号时才需要
    batch_id        TEXT,               -- 同一批投递共享，便于按批复盘
    attempted_at    TEXT NOT NULL,      -- ISO 8601
    settled_at      TEXT,               -- 状态终态时间
    last_seen_at    TEXT,
    UNIQUE(platform, job_id)
);

CREATE INDEX idx_company_title_city ON applications(company_norm, title_norm, city_norm);
CREATE INDEX idx_attempted_at ON applications(attempted_at);
```

字段取舍理由：

- `resume_version`：简历换了没换，直接决定"这个岗位投的是哪版"。没有这个字段，三个月后无法回答"我投那家的时候写的是 18 年还是 19 年经验"。
- `batch_id`：战报按批统计，也用于批内去重和"这批为什么只投了 31 个"的归因。
- `reason`：所有非 `success` 的状态都必须有原因。空原因是 bug。
- `last_seen_at`：重复岗位也要更新，用来识别"这个岗位挂了两个月还在招"。

**不记的字段**：HR 姓名、手机号、微信号、聊天原文。台账是投递记录，不是通讯录。

## 4. 投成即落盘 + 崩溃恢复

这是整条流水线最容易出假账的地方。规则：

### 写两次，不是写一次

```
1. 投递前：INSERT (status='pending', attempted_at=now)   ← 先落意图
2. 调 apply()
3. 拿到结果：UPDATE status=终态, settled_at=now
```

如果只写一次（投完再写），进程在第 2 步崩了，这条记录就凭空消失，下次重跑会重复投。
如果先写 pending，崩了之后台账里留着一条 pending，你知道"这条不确定"。

### 启动时的 pending 清理

每次 `run` 开始，扫描 `status='pending'` 且 `attempted_at` 超过 30 分钟的记录：

| 有证据文件 | 无证据文件 |
|---|---|
| 判 `success`（证据在，说明页面出现过成功态） | 判 `unknown`，**不重投**，进人工核验队列 |

`unknown` 记录不自动重试，也不计入当日投递数。宁可少投一个，不可重投一个——重投会污染数据，也会让 HR 收到两条重复记录。

### 幂等约束

`UNIQUE(platform, job_id)` 是最后一道保险。任何路径下重复插入都会失败，程序捕获后转 `duplicate`，不会产生第二次真实投递。

## 5. 六项战报口径

每日战报固定六项，口径固定，避免"今天看起来投了很多"的自我欺骗：

1. **投递数：目标 vs 实际 + 偏差原因**。实际 = `status='success'` 且 `attempted_at` 在当日。`unknown` 不计。偏差必须写原因（候选池不足 / 熔断 / 人工接管 / 时间不够）。
2. **重复拦截数**：`duplicate` 按来源分（历史台账 / 跨平台 / 批内）。这个数字高不一定是坏事，说明闸门在工作。
3. **站内消息分类处理数**：按「需回复 / 已回复 / 仅知晓 / 系统通知」四类计数。猎聘来源的消息单独标注，不与邮箱待办混算。
4. **邮件收发分类**：发送成功封数、退信数、需回复未回数。以实际发送成功计，不以"计划发送"计。
5. **黑名单生效确认**：当日被拦下的公司/岗位抽样 3 条，人工看一眼是否误杀。
6. **次日计划**：时段安排 + 候选池余量（还剩多少符合条件未投的岗位）。

口径的三条铁律：**以本地台账为准，不以平台页面数字为准；以成功态为准，不以点击次数为准；以当日为准，跨日不合并。**

---

## 6. 一页速查

```
投前：黑名单 → 历史台账 → 批内      （顺序不可换）
写账：pending → 执行 → 终态          （两次写，不是一次）
崩溃：有证据判 success，无证据判 unknown，unknown 不重投
唯一：UNIQUE(platform, job_id)       （数据库兜底）
战报：成功态计数，当日切分，偏差必写原因
```
